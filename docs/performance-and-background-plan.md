# План оптимизации производительности, фоновой работы и индикации прогресса

**Дата:** 2026-11-22  
**Целевая версия:** `v0.4.0`  
**Статус:** Архитектурный и инженерный план реализации (без изменения существующего кода)

## 1. Контекст и результаты профилирования реального примера (`Archive.zip`)

Проведён детальный разбор приложенного дампа большой сессии Arena (`5.60 МБ` HTML + бандлы Next.js/Turbopack) и замер текущего пайплайна расширения.

### 1.1. Характеристики эталонного дампа

| Метрика | Значение |
|---|---|
| Размер сохранённого HTML | `5 596 938 B` (`5.60 MB`) |
| Всего DOM-узлов на странице / внутри `div[role="log"]` | `32 383` / `31 329` |
| Сообщений (`[data-agent-transcript-message]`) | `12` (`6` User + `6` Assistant) |
| Секций активности `button[aria-expanded]` | `1 217` (`1 042` раскрыто, `175` свёрнуто в снимке) |
| Смонтированных панелей `div[style*="overflow: clip"]` | `1 067` |
| Блоков `<pre>` / `.prose` / `<svg>` внутри лога | `1 173` / `291` / `3 651` |
| Побочных `role="status"` внутри сообщений | `2` (*tool-call limit notice*) |
| Итоговый сырой Markdown (`serialize`) | `1 612 502 B` (`1.61 MB`, `28 472` строк, `~447.7k` токенов) |
| Fenced-блоков кода/вывода в Markdown | `1 155` блоков = `1 277 514 B` (`79.2%` всего файла: `571 command` = `451 KB`, `551 stdout` = `821 KB`, `13 stderr` = `1.6 KB`) |

> **Ключевой вывод из дампа:** «очень большая история» в агентском режиме Arena возникает не только из-за сотен коротких реплик (пагинация по 20 сообщений), но и когда всего **10–15 ходов агента содержат 1 000–3 000 вызовов инструментов** (`Ran commands N` → вложенные `Used Bash`, `Thought for …`). На ветке из 80–150 сообщений объём DOM превышает `150 000–250 000` узлов, а сырой Markdown достигает `8–20 МБ`.

### 1.2. Выявленные узкие места текущего кода

#### А. Получение истории и раскрытие спойлеров (`loader.js`, `expand.js`)
1. **Пагинация через слепой поллинг (`loader.js`):**
   - В бандле Arena обнаружены точные хуки пагинации: верхний маяк `div[data-earlier-messages-sentinel]` внутри `div[data-earlier-messages-boundary]` (с `IntersectionObserver` и `rootMargin: "200px 0px 0px"`), который вызывает `GET /api/chat/:id/messages?cursor=...&limit=20` (`TRANSCRIPT_PAGE_LIMIT = 20`).
   - Когда `hasEarlierMessages === false` (`COMPLETE_TRANSCRIPT_PAGINATION`), Arena **размонтирует** `data-earlier-messages-sentinel` и `data-earlier-messages-boundary` из DOM!
   - Сейчас `loader.js` не проверяет наличие `[data-earlier-messages-sentinel]` и всегда ждёт `2` холостых раунда по `1200–2500 мс` (`2.4–5.0 с` впустую даже когда вся история уже загружена или достигнут верх ветки), а внутри `waitFor` опрашивает DOM каждые `250 мс` через `querySelectorAll`.
2. **Фоновая вкладка и `IntersectionObserver`:**
   - Если пользователь закрыл попап и переключил вкладку браузера, Chromium троттлит `IntersectionObserver` и таймеры фоновой вкладки (раз в секунду и реже), из-за чего `scrollTop = 0` перестаёт своевременно триггерить подгрузку страниц.
3. **Глобальный `settle` и массовое монтирование DOM (`expand.js`, `serialize.js`):**
   - `expandAllSpoilers` раскрывает **все** спойлеры всей ветки сразу и держит тысячи тяжёлых панелей в живом DOM одновременно до конца сериализации, вызывая пиковый расход RAM вкладки (сотни МБ на больших ветках) и длительный layout/recalc styles.
   - После каждого прохода `AREX.settle(log, { quietMs: 250, maxMs: 3000 })` вешает `MutationObserver` с `subtree: true, attributes: true` на весь `div[role="log"]` из `30k–200k` узлов. Любая CSS-анимация (`rotate-90`, `animate-pulse` во время генерации) сбрасывает таймер вплоть до потолка `3000 мс`.

#### Б. Сериализация DOM → Markdown (`serialize.js`, `util.js`)
Профилирование `AREX.serialize` на дампе `Archive.zip` показало гигантский оверхед на клонировании поддеревьев и повторных селекторах (`11.8–12.8 с` в jsdom; пропорциональные фризы main thread в браузере на ветках в 5–10 раз больше):
- **`AREX.headerText(wrapper)` — 38% всего времени сериализации (`1 217` вызовов `wrapper.cloneNode(true)`):** для заголовка спойлера клонируется **весь `wrapper` вместе со всеми уже раскрытыми вложенными панелями и `<pre>`-блоками**, чтобы тут же удалить панели через `querySelectorAll(PANEL).remove()`. В групповых блоках (`Ran commands 10`) внутренние `<pre>` клонируются дважды и трижды (на уровне группы и на уровне каждого дочернего `Used Bash`).
- **Десятки тысяч лишних DOM-запросов на каждом узле обхода `walkInto`:**
  - `footerOf(el)` вызывается на *каждом* посещённом элементе → `9 903` вызова `querySelector('time')` и `8 336` вызовов `querySelector('button[aria-expanded]')`, хотя футер бывает только внизу карточки сообщения.
  - `isItemWrapper(el)` делает `7 605` вызовов `querySelector(':scope > button[aria-expanded]')` вместо проверки прямых детей (`el.firstElementChild`).
  - `isLeafRow(el)` делает `7 245` вызовов `querySelector('svg')`, `4 285` вызовов `querySelector('div, button, pre')` и `1 136` глубоких `cloneNode(true)` в `scrub(el)`, а затем `walk()` повторно вызывает `scrub(el)` ещё `1 136` раз на тех же самых строках.
  - `codeText(pre)` делает `1 137` вызовов `pre.cloneNode(true)`, хотя внутри обычных `<pre>` карточек `command`/`stdout`/`stderr` нет ни `svg`, ни `.select-none`.
- **Синхронная блокировка потока страницы:** `AREX.serialize` обходит все сообщения единым синхронным вызовом без возврата управления (`yield`) циклу событий и без промежуточного прогресса (`Markdown: converting…` висит статично).
- *Проверка прототипом на `Archive.zip` подтвердила:* замена `cloneNode` + `querySelector` на однопроходный безотказный обход прямых потомков ускоряет `serialize` **в ~7 раз** при **100% побайтовом совпадении** выходного Markdown.

#### В. Сжатие и оценка токенов (`compress.js`, `popup.js`)
1. **Многократный перепарсинг мегабайтной строки (до 7 раз за одно переключение режима):**
   - `deduplicateOutputs` вызывает `parseFencedBlocks(md)` → `applyBlockEdits(md)` **снова** вызывает `parseFencedBlocks(md)` и `lines.splice(...)` + `join('\n')`.
   - Затем `smartCompact` **третий** и **четвёртый** раз делает `split('\n')` + `parseFencedBlocks`, а `compactReadStubs` — **пятый** и **шестой** раз!
   - На каждое распознавание блока делается `lines.slice(i - 12, i).join('\n')` и прогоняются 3 глобальных `matchAll` регулярных выражения (`3 465` раз на `1 155` блоков).
2. **Двойной запуск сжатия и синхронный UI-фриз в `popup.js`:**
   - При клике `Download Markdown` функция `downloadPrepared()` заново запускает `AREX.compressMarkdown(...)` на главном потоке попапа, хотя `prepared.preview` для текущего режима уже рассчитан в `renderSizePreview()`.
   - На истории `5–15 МБ` переключение кнопок `Lossless / Smart / Stubs` блокирует UI попапа на `0.5–3+ с` без кэширования результатов по режимам.
3. **Тяжёлая регулярка в `estimateTokens(markdown)` (`~90%` времени режима `off`):**
   - Глобальный Unicode-матчер `value.match(/[\p{L}\p{N}_]+|[^\s\p{L}\p{N}_]+/gu)` аллоцирует массив из **сотен тысяч подстрок** (на `1.61 МБ` — ~350 000 элементов!), после чего на *каждом* чанке запускает ещё **4 регулярных выражения** (`cyrillic`, `cjk`, `latin`, `digits`). На `1.61 МБ` это занимает `~515 мс`, тогда как `TextEncoder().encode(md).length` — всего `3.2 мс`, а однопроходный сканер `charCodeAt` с той же формулой — `~65 мс` (**в 8 раз быстрее и 0 аллокаций массива**).
4. **Низкая степень сжатия реальных агентских сессий (`7.2%` на `Archive.zip`) из-за слепых зон эвристик:**
   - В `Archive.zip` агент читал файлы через Bash (`sed -n 240,540p service.py`, `cat ...`, `head`, `nl`) — **127 блоков `stdout` на `437 КБ`** (например, `service.py` читался 17 раз на `131.8 КБ`), но `compactReadStubs` смотрит только в `block.body` и `block.activity` (`Used Bash 100ms`), **не связывая `stdout` с предшествующим блоком `**command:**`**, и пропускает команды с префиксом `$ cd /repo && sed -n ...`.
   - `ERROR_SIGNAL` (`/error|failed|failure|exception|.../i`) срабатывает на **обычный исходный код** внутри `stdout` при чтении файлов (например, `class CustomError(Exception):` или `assert not any(... in failures)`): из `34` крупных `stdout`-блоков (`292 КБ`) `11` блоков (`95 КБ`, треть объёма!) были ложно пропущены `smartCompact`, хотя команда имела нулевой код возврата (в заголовке не было `exit N` / `shell error`) и просто печатала код файла.
   - Крупные `**command:**`-блоки с записью файлов через heredoc (`cat > file.py << 'PY' ...`, `48` блоков >2 КБ на `183 КБ`) никак не учитываются при повторной перезаписи того же файла в режиме `Stubs`.

#### Г. Жизненный цикл после закрытия попапа и отсутствие индикации (`main.js`, `popup.js`, `background.js`)
1. **Зависимость финализации от открытого попапа:**
   - Хотя сканирование в `content/main.js` продолжает идти при закрытии попапа (коммит `2f77406`), **сохранение результата в IndexedDB происходит только внутри `popup.js` (`AREX_RESULT_STORE.save`)**.
   - Пока пользователь снова не откроет попап:
     - сырой многомегабайтный Markdown продолжает висеть в куче вкладки Arena (`AREX._job.result`);
     - если после завершения скана пользователь закроет или перезагрузит вкладку Arena, не открыв предварительно попап, **готовый экспорт безвозвратно теряется**;
     - IndexedDB привязана к origin расширения (`chrome-extension://<id>`), поэтому контент-скрипт на `https://arena.ai` не может писать в неё напрямую — запись должен выполнять фоновый контекст расширения (`background.js`), а не `popup.js`!
2. **Потеря привязки к вкладке и смешанные снимки:**
   - В `IndexedDB` хранится единственный ключ `'latest'` без `tabId` / `chatUuid` / `sourceUrl`. Если экспорт шёл во вкладке A, а пользователь переключился на вкладку B, статус и сохранённый снапшот не сопоставляются с активным чатом или фоновой задачей.
3. **Полное отсутствие индикации на иконке расширения:**
   - `background.js` сейчас содержит только 16 строк переключения светлой/тёмной иконки и вообще не знает о запуске, прогрессе, завершении или ошибке экспорта. Во время многоминутного скана большой истории иконка выглядит полностью статичной.

## 2. Предлагаемые методы оптимизации и архитектурные решения

### 2.1. Архитектура непрерывной фоновой работы (Popup-Independent Lifecycle)

Переводим **Service Worker (`background.js`)** в роль центрального координатора состояния, хранилища и индикатора иконки, сохраняя нулевые внешние зависимости и отсутствие шага сборки:

```
┌──────────────────────┐       port / messages       ┌───────────────────────────────────┐
│  Content Script      │ ──────────────────────────▶ │  Background Service Worker        │
│  (arena.ai/agent/*)  │ ◀────────────────────────── │  (background.js + shared store)   │
│                      │  AREX_JOB_EVENT / RESULT    │                                   │
│ 1. loadFullHistory   │                             │ • Держит SW живым во время задачи │
│ 2. expand & serialize│                             │ • Хранит jobState по tabId/chatId │
│    (streaming/chunks)│                             │ • Сам пишет готовый MD в IndexedDB│
│ 3. collapse opened   │                             │ • Рисует индикатор и бейдж иконки │
└──────────────────────┘                             └─────────────────┬─────────────────┘
                                                                       │ port 'AREX_POPUP'
                                                                       ▼
                                                     ┌───────────────────────────────────┐
                                                     │  Popup UI (popup.js + Web Worker) │
                                                     │  • Подключается и мгновенно       │
                                                     │    рендерит актуальный прогресс   │
                                                     │  • Читает готовый снимок из IDB   │
                                                     │  • Считает сжатие в Web Worker    │
                                                     └───────────────────────────────────┘
```

1. **Единый координатор в `background.js`:**
   - Контент-скрипт открывает долгоживущий `chrome.runtime.connect({ name: 'AREX_JOB' })` к `background.js` на всё время экспорта.
   - **SW Keep-Alive в MV3:** пока открыт `runtime.Port` и по нему идут события прогресса (плюс страховочный heartbeat раз в `20 с` со стороны контент-скрипта во время длинных ожиданий сети), Chrome **гарантированно не выгружает Service Worker** до окончания задачи.
   - На случай внезапного перезапуска SW текущее состояние активных задач (`status`, `stage`, `percent`, `counters`, `tabId`, `chatUuid`, `startedAt`, последние события лога) зеркалируется в `chrome.storage.session` (быстрое in-memory хранилище MV3 до 10 МБ, переживающее рестарт SW).
2. **Немедленное сохранение результата в IndexedDB без участия попапа:**
   - IndexedDB (`result-store.js`) доступна одинаково из `background.js` (Service Worker global scope `self.indexedDB`) и из `popup.js` — у них **один и тот же origin `chrome-extension://<id>`**.
   - Как только `content/main.js` завершает сериализацию, он передаёт результат в `background.js` (для очень больших файлов `> 8 МБ` — чанками по `2 МБ` через `Port`, чтобы не упереться в сериализацию крупных IPC-сообщений Chrome).
   - `background.js` сразу записывает снимок в IndexedDB (ключуя по `chatUuid` + указатель `latest`), отправляет контент-скрипту `AREX_RESULT_ACK` для немедленной очистки памяти вкладки Arena и переводит статус задачи в `ready`.
   - **Даже если попап был закрыт на 1-й секунде и вкладку Arena закрыли сразу после завершения скана — результат уже надёжно сохранён в IndexedDB расширения.**
3. **Мгновенное восстановление актуального прогресса при открытии попапа:**
   - При открытии `popup.js` подключается портом `AREX_POPUP` к `background.js` с `tabId` текущей вкладки (а если текущая вкладка не Arena, но в фоне идёт экспорт в другой вкладке — показывает компактную плашку активного фонового экспорта с возможностью переключиться на вкладку).
   - `background.js` мгновенно отдаёт `AREX_STATE_SNAPSHOT` (текущий этап, точный процент, лог этапов с таймингами, счётчики страниц/спойлеров/байт) и стримит все последующие `AREX_PROGRESS` в реальном времени без задержки на `executeScript` или пинг вкладки.
   - Добавляется кнопка **Cancel** в попапе во время работы: сигнал `AREX_EXPORT_CANCEL` через `AbortController` прерывает цикл подгрузки/раскрытия, аккуратно сворачивает уже открытые экспортером спойлеры и сбрасывает индикатор иконки.

### 2.2. Визуальный индикатор работы на иконке расширения

Во время работы расширения комбинируем **два нативных механизма `chrome.action`**, которые отлично видны при любом размере панели Chrome (включая macOS Retina `16px`/`32px` и светлую/тёмную тему):

1. **Динамическая отрисовка иконки через `OffscreenCanvas` в `background.js` (`chrome.action.setIcon({ imageData })`):**
   - В MV3 Service Worker штатно доступен `OffscreenCanvas` и `createImageBitmap` — не требуется ни `OffscreenDocument`, ни десятков предрендеренных PNG-кадров в репозитории.
   - Базовый глиф документа (`light` `#5f6368` или `dark` `#c7c7c7`) кэшируется как `ImageBitmap` для размеров `16` и `32` px.
   - Во время активного экспорта поверх правого нижнего квадранта иконки с частотой `~4–6 FPS` (интервал `180 мс`, только пока `status === 'running'`, с защитой от наложения вызовов) рисуется чёткий **круговой индикатор активности** (контрастная подложка-ореол под цвет темы + вращающаяся дуга прогресса цвета акцента `#1a73e8` / `#8ab4f8`, угол дуги отражает расчётный прогресс пайплайна или плавный спиннер на этапе с неизвестным общим числом страниц).
2. **Информативный бейдж (`chrome.action.setBadgeText` + `setTitle`):**
   - В дополнение к canvas-оверлею (или как мгновенно читаемый текстовый статус) обновляется компактный бейдж и всплывающий тултип иконки (`chrome.action.setTitle`):
     - Этап 1 (история): бейдж `1/3` или число страниц `p4` (синий фон `#1a73e8`), тултип: `Arena Export — Loading history (120 messages)…`
     - Этап 2 (раскрытие/сериализация): процент `45%` (синий фон), тултип: `Arena Export — Processing message 54/120 (1 240 spoilers)…`
     - Готово (если попап был закрыт в момент финиша): зелёный бейдж `✓` (`#188038`) + зелёная точка на иконке до первого открытия попапа пользователем (чтобы пользователь сразу увидел, что большой экспорт завершился!).
     - Ошибка: красный бейдж `!` (`#d93025`) с причиной ошибки в `title`.
     - При открытии попапа в состоянии `done` или при переходе в `idle` иконка и бейдж возвращаются к чистому штатному виду с учётом текущей системной темы.

### 2.3. Оптимизация получения очень большой истории и работы с DOM

#### Метод 1. Детекция маяка `data-earlier-messages-sentinel` и событийный `MutationObserver` вместо слепого поллинга (`loader.js`)
Из анализа бандлов `242vfx3agffoe.js` и `4553ofnfaj1wn.js` известно точное устройство пагинации Arena:
- **Мгновенный выход при полной истории (`0 мс` вместо `2 400–5 000 мс`):** если в `log` отсутствует `[data-earlier-messages-sentinel]` и нет кнопки повтора (`retry`) и спиннера загрузки (`loading`), значит `hasEarlierMessages === false` — история гарантированно загружена до самого первого сообщения. Холостые проверочные раунды (`stagnantTarget = 2`) оставляем **только как фолбэк**, если Arena изменит атрибут маяка в будущем.
- **Событийное ожидание через `MutationObserver` на прямых детях колонки сообщений:** вместо поллинга `querySelectorAll('[data-agent-transcript-message]')` каждые `250 мс` подписываемся `MutationObserver({ childList: true })` на контейнер списка сообщений (`firstMsg.parentElement`) и контейнер маяка `[data-earlier-messages-boundary]`. Как только React вставил пачку из 20 старых сообщений и обновил маяк, следующий шаг цикла стартует **немедленно (через 1 кадр / microtask)** без ожидания `250 мс` шага поллинга. На ветке из 100 страниц (2 000 сообщений) это экономит **25+ секунд** чистого простоя на поллинге.
- **Принудительный триггер маяка даже в фоновой вкладке:** помимо `log.scrollTop = 0`, вызываем `sentinel.scrollIntoView({ block: 'start', behavior: 'instant' })` и диспатчим событие `scroll` на `log`, чтобы `IntersectionObserver` гарантированно срабатывал после каждого пересчёта `overflowAnchor` со стороны Arena.

#### Метод 2. Потоковая (по-сообщениям / скользящим окном) обработка: «Раскрыть → Сериализовать → Сразу свернуть» (Windowed Expand-Serialize-Collapse)
**Главная архитектурная оптимизация памяти и скорости для гигантских историй:**

Сейчас пайплайн работает глобально:
`Раскрыть ВСЕ 5 000 спойлеров всей ветки` → `Держать 250 000 DOM-узлов в памяти` → `Сериализовать всё разом` → `Свернуть 5 000 спойлеров`.

**Новый потоковый конвейер по окнам сообщений (например, по `W = 3–5` сообщений ассистента за окно):**
1. Загрузили все заголовки сообщений в `div[role="log"]` (сами сообщения со свёрнутыми спойлерами лёгкие — как видно из исследования Arena, тела свёрнутых спойлеров не смонтированы в DOM).
2. Идём по массиву сообщений `msgs[0 .. N-1]` окнами по `W` сообщений:
   - **Шаг А (Scoped Expand):** раскрываем `button[aria-expanded="false"]` **только внутри текущего окна сообщений**, а не во всём `log`!
   - **Шаг Б (Scoped Settle):** ждём стабилизации DOM **локально на узлах текущего окна** с коротким `quietMs = 80–120 мс` и `attributes: false` (`childList: true, subtree: true`). Анимации генерации в последнем сообщении или CSS-переходы иконок больше не задерживают `settle` на `3 000 мс`!
   - **Шаг В (Chunked Serialize):** сразу сериализуем сообщения этого окна в массив строковых чанков Markdown (`parts.push(...)`).
   - **Шаг Г (Immediate Collapse):** тут же закрываем открытые в этом окне спойлеры в обратном порядке — React размонтирует тяжёлые `<pre>` и подсветку кода до перехода к следующему окну!
   - **Шаг Д (Cooperative Yield + Progress):** отдаём квант времени браузеру (`scheduler.yield?.()` или `MessageChannel` — не троттлится до 1000 мс в фоновых вкладках в отличие от вложенных `setTimeout`!) и шлём точный прогресс `processedMessages / totalMessages` и накопленный размер байт.

**Эффект:**
- Пиковое потребление памяти DOM снижается с $O(\text{все спойлеры всей истории})$ до **$O(\text{спойлеры 3 сообщений})$** — вкладка Arena перестаёт распухать до гигабайтов и зависать на огромных сессиях.
- Сериализация больше никогда не блокирует главный поток монолитным многосекундным вызовом.
- Пользователь видит плавный сквозной прогресс `0% → 100%` по мере прохождения сообщений.

#### Метод 3. Безклоновая (Zero-Clone) однопроходная сериализация DOM (`serialize.js`, `util.js`)
Полностью устраняем выявленные при профилировании `Archive.zip` горячие точки при сохранении 100% идентичности Markdown:
1. **`AREX.headerText(wrapper)` без `cloneNode`:** обходим `childNodes` обёртки рекурсивно, пропуская на лету `tagName === 'svg'`, панель `div[style*="overflow: clip"]` и кнопку `button[aria-label="Open file"]`. Экономия: **минус 100% глубоких клонирований спойлеров** (`-38%` общего времени сериализации).
2. **`codeText(pre)` с быстрым путём:** сначала проверяем быстрый предикат `!pre.querySelector('svg, button, .select-none')` (истинно для >99% карточек `command`/`stdout`/`stderr`) и сразу берём `pre.textContent` / `innerText` без клонирования мегабайтных `<pre>`.
3. **Замена `querySelector` в горячем цикле `walkInto` на проверку прямых свойств узла:**
   - `isItemWrapper`: итерируем `el.firstElementChild .. nextElementSibling` в поисках `BUTTON` с `hasAttribute('aria-expanded')` (вместо `:scope > button[aria-expanded]`).
   - `footerOf`: проверяем только на верхнем уровне карточки сообщения (или быстрым фильтром `el.tagName === 'DIV'` + `getElementsByTagName('time').length > 0` до любых CSS-селекторов).
   - `isLeafRow` + `renderLeaf`: объединяем проверку и извлечение текста в одну функцию `extractLeafRowText(el)` с безклоновым обходом текстовых узлов (убирает двойной `cloneNode` на каждой строке `Read x.sh`).
   - `cardLabel(pre)`: при обходе панели запоминаем метку карточки сверху вниз в контексте обхода, вместо всплытия вверх с `querySelectorAll('span')` от каждого `<pre>`.

### 2.4. Оптимизация обработки (сжатия) и выноса вычислений в Web Worker (`compress.js`)

#### Метод 4. Однократное построение индекса блоков (`BlockIndex`) и O(N) сборка всех режимов
Вместо многократного `markdown.split('\n')`, `parseFencedBlocks` и мутации массива через `lines.splice(...)`:
1. **Единый проход парсинга (`AREX.indexMarkdown(rawMarkdown)` — `~35–40 мс` на `1.6 МБ`):**
   - Один раз разбиваем документ или сканируем смещения строк.
   - В одном линейном проходе отслеживаем текущий заголовок активности (`###..######`), последнюю метку `**command:**` / `**stdout:**` / `**stderr:**`, карточку файла `**📄 ...**` и **связываем каждый блок `stdout`/`stderr` с предшествующим ему блоком `command` того же вызова инструмента** (`pairedCommand`).
   - Сразу считаем UTF-8 байты и вклад в токены неизменяемых участков текста (между fenced-блоками) и каждого блока в отдельности!
2. **Мгновенная сборка любого режима за $O(B)$ (`B` — число блоков) и кэширование по режимам:**
   - Трансформации (`lossless`, `smart`, `stubs`) больше не пересобирают и не перепарсивают весь Markdown между этапами — они работают как конвейер чистых функций над массивом объектов `BlockDescriptor[]`, меняя только поле `replacement` у затронутых блоков!
   - Итоговая строка собирается **ровно один раз** в конце линейным склеиванием слайсов неизменённых диапазонов и изменённых блоков (никаких `Array.prototype.splice` на массиве из 100 000 строк).
   - Токены и байты сжатой версии вычисляются **инкрементально**: `compressedBytes = rawBytes - sum(deltaBytes)`, `compressedTokens = rawTokens - sum(deltaTokens)` — пересчитываются только изменённые блоки!
   - В попапе результаты `off / lossless / smart / stubs` кэшируются по `snapshotId`: повторный клик по режиму и нажатие `Download Markdown` работают за **`0 мс`** (берут уже готовый `Blob` / строку из кэша без повторного вызова `compressMarkdown`).
3. **Быстрое хеширование длинных блоков при дедупликации (`Lossless`):**
   - Вместо использования многокилобайтных строк `block.body` напрямую как ключей `Map` для всех блоков подряд, используем ключ `bytes + ':' + fnv1a32(body)` с проверкой полного равенства строк только при совпадении длины и хеша. Это снижает нагрузку на интернирование строк и сравнения.

#### Метод 5. Быстрый безрегулярочный оценщик токенов (`estimateTokens`)
- Заменяем `value.match(/[\p{L}\p{N}_]+|.../gu)` + 4 внутренних `.match(...)` на **однопроходный сканер кодовых точек (`charCodeAt` / `codePointAt`)** без создания промежуточных подстрок и массивов.
- Сохраняется та же мульти-языковая эвристика (латиница / кириллица / CJK / цифры / пунктуация), расхождение `< 0.1%`, ускорение **в 8–12 раз** и нулевое давление на сборщик мусора (GC).

#### Метод 6. Вынос сжатия и расчёта метрик в `Web Worker` (`extension/worker/compress-worker.js`)
- `compress.js` уже не зависит от DOM (`window`/`document`, кроме экспорта в `self.AREX = self.AREX || {}`).
- Делаем `compress.js` универсальным (`const root = typeof globalThis !== 'undefined' ? globalThis : self; root.AREX = ...`).
- Для небольших историй (`< 256 КБ`) можно считать синхронно (`< 5 мс`), а для крупных (`≥ 256 КБ`) `background.js` (при предрасчёте метрик после скана) или `popup.js` запускает `new Worker('../content/compress-worker.js')`, который за один вызов предрасчитывает метрики для всех режимов в фоновом потоке, оставляя анимации и кнопки попапа идеально отзывчивыми (`60 FPS`).

#### Метод 7. Улучшение качества самого сжатия на больших агентских историях (по данным `Archive.zip`)
Анализ `Archive.zip` показал, как поднять реальную экономию режимов `Smart` и `Stubs` с `7%` до `25–45%` без потери диагностической ценности:
1. **Связка `command → stdout` в `Stubs` для Bash-чтений файлов:**
   - Распознавать команды чтения файла в `pairedCommand` с учётом типичных префиксов агента (`$ cd /path && `, `export ...; `): `cat <file>`, `sed -n 'X,Yp' <file>`, `head`/`tail`/`nl <file>`.
   - Если один и тот же файл многократно читался целиком (`cat`) или перекрывающимися диапазонами (`sed -n`), либо позже перезаписывался/перечитывался без ошибок — сворачивать ранние дублирующие/перекрытые дампы в компактный стаб (как уже делается для карточек `Read`), сохраняя последнее актуальное чтение полностью.
2. **Точное определение ошибок команды вместо наивного поиска слова `error` в тексте файла (`Smart` / `Stubs`):**
   - Сейчас `ERROR_SIGNAL` блокирует сжатие любого `stdout`, где в прочитанном исходном коде встретилось слово `error`, `exception` или `failure` (`95 КБ` ложных срабатываний в `Archive.zip`!).
   - Разделяем контекст:
     - если заголовок активности содержит ненулевой код выхода (`exit [1-9]`, `shell error`, крестик ошибки) или блок помечен `**stderr:**` — **всегда сохраняем полностью**;
     - если команда — чистое чтение файла (`cat` / `sed -n` / `head` / `nl`) с успешным статусом — содержимое является текстом файла, а не крэшем команды;
     - для прочих `stdout` проверяем структурные маркеры реальных ошибок исполнения (`Traceback (most recent call last):`, `^E   `, `FAIL `, `error[E\d+]:`, `SyntaxError:`, `ReferenceError:`, `TypeError:`, `npm ERR!`, `panic:`, `Segmentation fault`, `AssertionError`), не путая их с идентификаторами вроде `error_handler` или строками документации.
3. **Дедупликация и стабы для повторных heredoc-записей одного файла (`Stubs`):**
   - В `Archive.zip` `48` блоков `**command:**` (`183 КБ`) — это запись файлов через `cat > path/to/file << 'EOF'`. Если агент несколько раз за сессию перезаписывает один и тот же файл целиком через `cat > file << 'EOF'`, в режиме `Stubs` более ранние промежуточные версии heredoc-тела можно сворачивать с указанием финальной записи (оставляя саму строку команды и полный последний вариант файла).

## 3. Пошаговый план реализации

План разбит на **5 независимых этапов (PR / коммитов)**, каждый из которых сохраняет работоспособность расширения и покрывается модульными тестами `node:test`.

### Этап 1. Фоновый координатор в `background.js`, хранение в IndexedDB и синхронизация прогресса с попапом
**Цель:** расширение продолжает полный цикл работы (включая запись результата в IndexedDB!) при закрытом попапе, а при открытии попапа мгновенно отображает актуальный прогресс или готовый результат.

- **Файлы:**
  - `extension/shared/result-store.js` (перенос и обобщение `popup/result-store.js` на `globalThis`, поддержка `self.indexedDB` в Service Worker и `window.indexedDB` в попапе; хранение метаданных `tabId`, `chatUuid`, `sourceUrl`, `createdAt` + быстрый запрос метаданных без вычитки мегабайтной строки `markdown` без необходимости).
  - `extension/background.js`:
    - Реестр активных и завершённых задач `jobsByTab` + персистентность оперативного статуса в `chrome.storage.session` (для защиты от рестарта MV3 Service Worker).
    - Обработка порта `AREX_JOB` от контент-скрипта: приём `AREX_PROGRESS`, чанкованный приём `AREX_RESULT_CHUNK` / `AREX_RESULT_END`, запись снимка в IndexedDB через `AREX_RESULT_STORE.save(...)`, отправка `AREX_RESULT_ACK` обратно во вкладку для немедленного освобождения RAM вкладки Arena.
    - Обработка порта `AREX_POPUP` от попапа: мгновенная отдача `AREX_STATUS` по `tabId` (или активной фоновой задаче), ретрансляция live-событий `AREX_PROGRESS`, проксирование команд `AREX_EXPORT_START` и `AREX_EXPORT_CANCEL` в нужную вкладку (включая инжект контент-скриптов через `chrome.scripting.executeScript`, перенесённый из `popup.js` в `background.js`).
    - Очистка `jobsByTab` при `chrome.tabs.onRemoved` / смене URL вкладки (с пометкой ошибки `Tab was closed before scan finished`, если задача была `running`).
  - `extension/content/main.js`:
    - Подключение к `background.js` через `chrome.runtime.connect({ name: 'AREX_JOB' })` при старте `runExport` + heartbeat каждые `20 с` до завершения задачи.
    - Поддержка `AbortController` для штатной отмены (`AREX_EXPORT_CANCEL`) с корректным вызовом `collapseOpenedSpoilers` в блоке `finally`.
    - Потоковая передача результата в `background.js` чанками по `2 МБ` для больших историй.
  - `extension/popup/popup.html`, `extension/popup/popup.js`:
    - Перевод UI на порт с `background.js` вместо прямого `tabs.connect` из попапа.
    - Добавление прогресс-бара (`<div id="progressBar">`) и кнопки `Cancel` рядом со статусом во время `running`.
    - Корректное отображение прогресса даже при многократном закрытии/открытии попапа на любом этапе (`history`, `expand`, `serialize`, `cleanup`, `saving`).
  - `extension/manifest.json`: проверка разрешений (`storage`, `scripting`, `downloads` — новых опасных разрешений **не требуется**, так как `chrome.storage.session` входит в `storage`, а `OffscreenCanvas` работает без `offscreen`).

### Этап 2. Индикатор активности и прогресса на иконке расширения
**Цель:** наглядная визуальная индикация работы, прогресса и завершения прямо на иконке тулбара Chrome с поддержкой светлой и тёмной тем.

- **Файлы:**
  - `extension/background.js` (или выделенный модуль `extension/shared/icon-indicator.js`, подключаемый через `importScripts` в `background.js`):
    - Загрузка базовых PNG (`icon16.png`, `icon32.png` и `-dark` вариантов) через `fetch(chrome.runtime.getURL(...))` → `createImageBitmap` с кэшированием в памяти SW.
    - Рендерер `OffscreenCanvas(size, size)`:
      - в состоянии `running`: базовый глиф + контрастный бейдж-кольцо в правом нижнем углу с вращающейся/заполняющейся дугой прогресса (`#1a73e8` light / `#8ab4f8` dark); таймер анимации `180 мс` активен **строго пока есть хотя бы одна задача в статусе `running`**;
      - в состоянии `done_unseen` (завершилось при закрытом попапе): зелёный индикатор готовности + бейдж `✓`; сбрасывается при открытии попапа;
      - в состоянии `error_unseen`: красный индикатор + бейдж `!`;
      - в состоянии `idle`: возврат к статическому `chrome.action.setIcon({ path })` текущей темы и очистка бейджа `setBadgeText({ text: '' })`.
    - Синхронное обновление `chrome.action.setTitle` с человекочитаемым прогрессом (`Loading history: 80 msgs…`, `Scanning 64% (12/18 msgs)…`, `Ready to download (1.42 MB)`).

### Этап 3. Оптимизация загрузки большой истории и потокового обхода DOM (`loader.js`, `expand.js`, `serialize.js`, `util.js`)
**Цель:** кратное ускорение сбора больших веток и снижение пикового потребления RAM вкладки Arena.

- **Файлы:**
  - `extension/content/selectors.js`:
    - Добавление селекторов маяка пагинации Arena: `SENTINEL: '[data-earlier-messages-sentinel]'`, `BOUNDARY: '[data-earlier-messages-boundary]'` (с сохранением обратной совместимости при их отсутствии).
  - `extension/content/loader.js`:
    - Быстрый выход за `0` холостых раундов, если `[data-earlier-messages-sentinel]` отсутствует, спиннера `Loading earlier messages` нет, кнопки `Load earlier messages` нет и число сообщений стабильно после короткого `settle(150ms)`.
    - Замена `waitFor(..., pollMs: 250)` на событийный `waitForDomChange` (`MutationObserver` на списке сообщений и `boundary`) + принудительный `sentinel.scrollIntoView({ block: 'start' })`.
  - `extension/content/util.js` и `extension/content/serialize.js`:
    - Рефакторинг `AREX.headerText`, `scrub`, `codeText`, `isItemWrapper`, `footerOf`, `isLeafRow`, `cardLabel` на **безклоновый (Zero-Clone) обход DOM** (проверено на дампе `Archive.zip`: ускорение сериализации в ~7 раз при 100% совпадении вывода).
    - Неблокирующий кооперативный планировщик `AREX.yieldToMain()` на базе `scheduler.yield()` / `MessageChannel` (не троттлится в фоновых вкладках до 1 с, в отличие от `setTimeout`), вызываемый каждые `~16–25 мс` бюджетного времени.
  - `extension/content/expand.js` и `extension/content/main.js`:
    - Внедрение **оконного конвейера `processMessagesInWindows(log, options)`** (размер окна `W = 4` сообщения):
      1. Раскрытие спойлеров только внутри сообщений окна `[i .. i + W - 1]`.
      2. Локальный `settle` на контейнерах этих `W` сообщений (`attributes: false`, `quietMs: 100`, `maxMs: 1500`).
      3. Немедленная сериализация этих `W` сообщений в Markdown-сегменты.
      4. Немедленное сворачивание открытых в этом окне спойлеров (`collapseOpenedSpoilers` для окна) — освобождение DOM-памяти до перехода к следующему окну.
      5. Эмиссия детального прогресса `{ stage: 'process', processedMessages, totalMessages, expandedSpoilers, assembledBytes, percent }`.
    - Сохранение публичных `AREX.expandAllSpoilers` и `AREX.serialize` для обратной совместимости существующих unit-тестов.

### Этап 4. Оптимизация движка сжатия, `BlockIndex` и вынос в `Web Worker` (`compress.js`)
**Цель:** убрать квадратично-многопроходный репарсинг мегабайтных строк, ускорить расчёт токенов и сжатия в 10+ раз и полностью разгрузить UI-поток попапа.

- **Файлы:**
  - `extension/content/compress.js`:
    - Переход на `globalThis.AREX` для совместимости с `Window`, `ServiceWorkerGlobalScope` и `DedicatedWorkerGlobalScope`.
    - Однопроходный парсер `AREX.buildMarkdownIndex(rawMarkdown)` → массив `blocks` с предвычисленными UTF-8 байтами, вкладом в токены, `label`, `fileName`, `activity` и ссылкой на парный `pairedCommand`.
    - Рефакторинг `deduplicateOutputs`, `smartCompact`, `compactReadStubs` для работы поверх единого `BlockIndex` с **однократной финальной сборкой строки** без промежуточных `split('\n')` / `splice` / `join('\n')`.
    - Быстрый `estimateTokens` на `charCodeAt`/`codePointAt` без аллокации сотен тысяч подстрок.
    - Улучшенные эвристики сжатия агентских сессий (связка `command → stdout` для Bash-чтений `cat`/`sed -n`/`head`/`tail`/`nl`, устранение ложных срабатываний `ERROR_SIGNAL` на исходном коде внутри успешных чтений файлов, стабы для перезаписанных heredoc-файлов в режиме `Stubs`).
  - `extension/popup/compress-worker.js` + интеграция в `popup.js`:
    - Фоновый воркер, принимающий сырой `markdown` один раз при загрузке снимка (`INIT_SNAPSHOT`), строящий `BlockIndex` в памяти воркера и возвращающий готовые метрики/строки по запросу режима с кэшированием всех 4 режимов (`off`, `lossless`, `smart`, `stubs`).
    - Устранение повторного вызова `compressMarkdown` внутри `downloadPrepared()` — скачивание использует уже подготовленный кэшированный результат.

## 4. Ожидаемый эффект (сводка целевых метрик)

| Узел пайплайна | Сейчас (`v0.3.0`) | После реализации плана (`v0.4.0`) |
|---|---|---|
| Подтверждение конца истории (`loader.js`) | `2 400 – 5 000 мс` холостого ожидания + `250 мс` поллинг на каждую страницу | **`< 50 мс`** по маяку `sentinel` + мгновенная реакция через `MutationObserver` |
| Пиковая память DOM при раскрытии спойлеров | Все спойлеры всей ветки одновременно в DOM (`O(N)` панелей, риск OOM на 100+ ходах) | **Только `3–5` сообщений в окне (`O(1)` панелей)** — сворачиваются сразу после сериализации окна |
| Сериализация большого транскрипта (`1.6 МБ` MD / `1 217` спойлеров) | Монолитный синхронный вызов, `4 630` `cloneNode(true)`, `46 793` `querySelector*` | **Ускорение в ~6–8 раз**, `0` глубоких `cloneNode` на заголовках/строках, без блокировки main thread |
| Сжатие + расчёт токенов при переключении режимов (`1.6–10 МБ` MD) | До `7` полных репарсингов + `350k+` regex-аллокаций на каждый клик в UI-потоке попапа + повтор при скачивании | **1 парсинг в Web Worker**, переключение режимов и скачивание за **`0–5 мс`** из кэша, `0` фризов UI |
| Эффективность `Smart` / `Stubs` на Bash-агентских ветках (`Archive.zip`) | `7.0%` / `7.2%` (пропускает `cat`/`sed -n` и код со словом `error`) | **`25% – 45%`** (распознаёт повторные Bash-чтения файлов и реальные ошибки исполнения) |
| Закрытие попапа во время долгого экспорта | Скан идёт во вкладке, но результат не пишется в IndexedDB до повторного открытия попапа | **Полная автономность:** `background.js` держит связь, сам сохраняет снимок в IndexedDB, освобождает память вкладки и восстанавливает живой прогресс при открытии попапа |
| Индикация на иконке расширения | Отсутствует | **Анимированный прогресс-оверлей (`OffscreenCanvas`) + информативный бейдж (`%` / `✓` / `!`) + live-тултип** |
